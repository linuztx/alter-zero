# The compact o200k_base token counter

`src/tokenizer.rs` is the seam every status-tally count funnels through
(`app::count_tokens` → `tokenizer::count` — input, reply, reasoning deltas,
tool output, the Ctrl+D context estimate). It counts with tiktoken's
**`o200k_base`** encoding: exact for current OpenAI models, close for the
Llama / Claude / Qwen / DeepSeek models the providers serve, and only ever a
*live estimate between usage frames* — a real backend's `StreamEvent::Usage`
snaps the tally to the provider's own accounting (docs/prompt-caching.md).

## Why not tiktoken-rs's `CoreBPE`

The first implementation loaded `tiktoken_rs::o200k_base()` behind a
`OnceLock`, warmed at startup. Measured with a `/proc/self/status` probe, that
single object cost **45.5 MB resident** — the majority of the app's ~54 MB
startup RSS — because `CoreBPE` keeps:

- `encoder: FxHashMap<Vec<u8>, u32>` — every one of the ~200k token byte
  strings as its own heap `Vec<u8>`, in a hash map;
- `decoder: FxHashMap<u32, Vec<u8>>` — a **second** full copy of every token
  (a counter never decodes);
- `sorted_token_bytes: Vec<Vec<u8>>` — a **third** full copy, marked
  `#[allow(dead_code)]` upstream;
- `regex_tls`/`special_regex_tls` — **128 clones each** of the compiled split
  regexes (`MAX_NUM_THREADS`), for lock-free thread-local access we never
  needed (all app counts run on the loop thread or one backend thread);
- the 3.6 MB base64 rank text, `include_str!`-embedded and fully walked at
  parse time.

## The compact store

The same encoding, one copy of the data, count-only:

- **`assets/o200k_base.cbpe`** — the vocabulary as `[len: u8][token bytes]`
  per rank, in rank order (ranks are dense, so the rank *is* the index; the
  max token is 129 bytes, so a `u8` length always fits). 1.6 MB embedded vs
  tiktoken's 3.6 MB text. Generated by `scripts/gen-o200k-asset.py` from
  tiktoken's canonical `o200k_base.tiktoken` (MIT; sha256 in the script
  header); regenerating is only ever needed if the frozen encoding somehow
  changed.
- **`starts: Vec<u32>`** — one offset per rank into the embedded blob (the
  token bytes are *slices of the asset*, never copied to the heap).
- **`table: Vec<u32>`** — an open-addressed, linear-probe hash table of rank
  numbers (FNV-1a over the token bytes, power-of-two capacity at ~2.6× the
  vocabulary, `u32::MAX` = empty). Keys are not stored; a probe hit is
  confirmed by comparing the candidate rank's blob slice.
- **one** compiled `fancy_regex::Regex` for the split pattern (verbatim
  tiktoken's `O200K_BASE_PAT_STR`; its `(?i:…)` groups and `(?!\S)` lookahead
  are why the engine is fancy-regex — the same one tiktoken-rs uses).

Together: ~0.8 MB starts + ~2 MB table + the 1.6 MB asset pages + the regex ≈
**~5 MB resident**, a ninth of `CoreBPE`, measured the same way. Loading is a
single pass over the blob plus ~200k table inserts — no per-token allocation
at all — so `tokenizer::warm`'s background spawn in `main.rs` stays cheap.

`count` also never materialises tokens: it splits with the pattern and sums
per-piece token *counts* (`encode_ordinary` returns a `Vec<u32>` — +4 bytes
per token of transient spike when tallying a large tool output; the counting
merge just walks its span structure).

## The merge is a faithful port

Byte-pair counting is tiktoken's own algorithm, ported from the vendored
`byte_pair_merge` in tiktoken-rs (MIT), both tiers:

- pieces `< 100` bytes: the quadratic scan (`count_merge_small`) — upstream's
  deliberate choice, cache-friendly at word sizes;
- pieces `≥ 100` bytes (a `===…` banner, a minified bundle's symbol run): the
  heap-driven merge (`count_merge_large`), O(m log n).

Tie-breaking is part of the port, not an accident: equal-rank merges resolve
**leftmost-first** in both tiers (the heap orders by `(rank, start)`), because
merge order changes *which* tokens equal-rank merges produce, later merges see
those tokens, and the token count can diverge downstream. The one deliberate
divergence: where tiktoken `unwrap()`s a fancy-regex backtrack-limit error
(unreachable for this pattern in practice), `count` degrades to a coarse
`bytes/4` estimate for the unscanned tail instead of panicking mid-tally.

## Proven equivalent, permanently

`tiktoken-rs` stays as a **dev-dependency**, and `src/tokenizer.rs`'s tests
hold the two implementations equal:

- `embedded_vocabulary_matches_tiktoken_rs_rank_by_rank` — every rank's bytes
  equal `CoreBPE::decode_bytes` for that rank, so a bad asset regeneration
  cannot land silently;
- `every_rank_is_findable_through_the_hash_table` — round-trips every rank,
  ruling out silent shadowing by duplicate tokens;
- `counts_match_tiktoken_rs_across_a_broad_corpus` — prose, code, contractions,
  digit runs, whitespace-lookahead boundaries, CJK/Arabic/Thai/Devanagari,
  emoji ZWJ/flags/tones, combining marks, control bytes, plus pieces past the
  100-byte threshold to force the large-merge tier in both implementations;
- `counts_match_tiktoken_rs_on_seeded_random_text` — 300 deterministic
  LCG-driven strings over a mixed alphabet.

The original golden-value tests (`hello world` = 2, etc.) still pin absolute
correctness independent of the reference crate.
